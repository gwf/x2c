# Size-normalized build metrics

> Status: done 2026-09-23. `tools/build-scaling.py` and
> `make bm-build-scaling` run as the `build-scaling` step of the nightly
> performance snapshot. Guidance is in `agents/performance-checkpoints.md`.

## Goal

Tell apart a stage 3 build that got slower because the compiler got slower
from one that got slower because the code base grew.

## Evidence from the spike

Measured on the M4 Max host at `0bdc8398`:

- `make stage-3` builds all four stages. Each stage translates `lib/` and
  `src/` in two serial batches (4.2 s and 3.8 s) and then compiles 95 C
  files (12.5 s of CPU, in parallel).
- Per-file C compile time against generated C bytes: R^2 0.96. Against x2c
  source lines: R^2 0.73. `lib/typed-array.x` is 226 lines and produces
  270 KB of C.
- Nightly history went from 17.1 s to 20.8 s between 2026-09-22 and
  2026-09-23 while source grew 3.4% (75.5k to 78.1k lines). Size does not
  explain that change.
- The same commit measured 17.12 s and 16.87 s on two runs.

## Design

- Translation is normalized by source lines, C compilation by generated C
  bytes, and generated bytes per source line is tracked separately because
  output growth makes every later compile more expensive.
- A pinned tree translated by the current compiler is the fixed workload. It
  catches slowdowns that grow faster than size, which no ratio can separate.
  The pin moves when the language drifts; the moving commit records both
  pinned times from one run.
- Measurements run in extracted trees outside the checkout with `X2C_HOME`
  set, so the compiler uses each tree's own runtime. C compilation runs
  serially through a timing wrapper so per-file times are not inflated by
  contention.
- The existing `stage_3_seconds` row is unchanged. Thresholds wait for the
  observation period the checkpoint guidance already requires.
